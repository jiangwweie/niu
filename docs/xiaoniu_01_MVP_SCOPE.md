## 1. 文档目的

本文档用于明确“小牛电动官方授权店两轮车维修售后库存管理系统”第一版 MVP 的范围边界。

本阶段目标不是设计数据库、接口或代码实现，而是先回答：

1. 第一版必须做什么？
2. 第一版暂缓做什么？
3. 第一版明确不做什么？
4. 哪些能力只做扩展预留？
5. 哪些需求变更必须重新评估？
6. AI Agent 在执行时不能擅自扩展哪些能力？

MVP 范围一旦冻结，后续 Codex 和 Claude 的所有任务都必须以本文档为约束。

## 2. 项目定位

本系统面向“小牛电动官方授权售后门店”，同时兼容第三方维修业务。

系统第一阶段目标是帮助单门店完成以下业务闭环：

```text
配件入库
  ↓
库存查询
  ↓
创建维修工单
  ↓
提交工单并预占库存
  ↓
维修处理
  ↓
客户支付 / 退款
  ↓
工单结算
  ↓
库存正式扣减
  ↓
官方售后结算录入
  ↓
报销确认
  ↓
财务报表统计
  ↓
Excel 导出
```

当前系统不是大型 ERP，不是多门店平台，不是低代码系统，也不是官方系统同步平台。

---

## 3. MVP 总体边界

第一版 MVP 采用：

```text
单门店
单后端
单数据库
微信小程序员工端
网页管理端
人工录入为主
财务基础统计
Excel 导出
```

第一版重点是让门店真实可用，而不是一次性实现完整商业化平台。

MVP 的判断标准：

```text
是否能支撑门店完成维修售后、库存和基础财务闭环？
是否能减少纸质记录和手工 Excel？
是否能保证库存、支付、退款、官方结算和报销的账目不混乱？
是否能为后续多门店、审批、自动化能力留下扩展空间？
```

## 4. MVP 必须做的功能

### 4.1 用户登录与权限

第一版必须支持：

- 员工账号登录
- 手机号登录
- 微信登录
- 微信登录后绑定手机号
- 角色管理
- 权限点管理
- 不同角色访问不同功能
- 操作记录中保留操作人信息

默认角色：

```text
超级管理员
门店管理员
财务
维修员 / 前台
```

权限至少覆盖：

```text
配件管理
工单管理
库存调整
财务报表
报销确认
系统配置
```

说明：

- 权限系统采用“角色 + 权限点”设计。
- 不追求复杂组织架构。
- 不做多门店权限体系，但预留 `store_id`。

---

### 4.2 字典与基础配置

第一版必须支持基础字典配置，避免关键业务项写死。

必须纳入字典或统一配置的内容：

```text
工单状态
支付方式
配件来源
配件分类
角色
权限点
门店
报销状态
库存流水类型
```

第一版只需要简单字典表，不做复杂配置平台。

---

### 4.3 配件管理

第一版必须支持：

- 官方配件管理
- 第三方配件管理
- 官方配件录入官方品号
- 第三方配件由系统自动生成编码
- 配件名称
- 配件型号
- 配件分类
- 成本价记录
- 条形码记录或生成
- 配件启用/停用
- 库存位置备注

配件来源：

```text
官方配件
第三方配件
```

重要规则：

- 第三方配件编码由系统自动生成。
- 官方配件可使用官方品号。
- 配件销售价不从默认价格表强制带出，工单中手动填写销售价。
- 工单临时配件也必须进入统一配件体系，不做孤立数据。

---

### 4.4 配件入库

第一版必须支持：

- 扫码入库
- 手动输入品号/型号入库
- 选择配件来源：官方配件 / 第三方配件
- 录入数量
- 录入成本价
- 录入条形码
- 记录入库时间
- 记录操作人
- 记录库存位置备注
- 生成库存流水

入库方式包括：

```text
正常入库
工单临时新增配件入库
```

---

### 4.5 库存管理

第一版必须支持：

- 当前库存查询
- 可用库存查询
- 预占库存查询
- 实际库存查询
- 库存流水查询
- 库存调整
- 库存调整原因记录
- 授权账号才可调整库存

库存核心规则：

```text
添加配件到工单草稿：不预占库存
提交工单：预占库存
工单结算：正式扣减库存
工单取消：释放预占库存
库存调整：必须记录原因和流水
```

库存数量建议逻辑：

```text
actual_qty      实际库存
available_qty   可用库存
reserved_qty    预占库存
```

说明：

- 第一版不做复杂盘点流程。
- 第一版只做简单数量加减 / 库存调整。
- 所有库存变化必须有库存流水。

---

### 4.6 工单系统

第一版必须支持：

- 创建工单
- 工单编号自动生成
- 客户姓名
- 客户联系方式
- 车型
- 车架号
- 电池号
- 维修项目
- 使用配件列表
- 工单内手动填写配件销售价
- 人工费
- 其他费用
- 支付信息关联
- 官方售后订单号备注
- 工单备注
- 工单状态流转
- 工单取消
- 工单结算
- 按车架号查询历史维修记录

工单状态第一版采用：

```text
待接单
已接单
已定件
已到件
已结算
已取消
```

说明：

- 工单状态可后续细化，但第一版不引入复杂状态机。
- 工单结算必须受到支付结果约束。
- 维修记录应绑定车架号。

---

### 4.7 工单临时配件

第一版必须支持工单中临时新增配件。

规则：

- 临时配件可直接录入并入库。
- 临时入库数量默认等于本次工单使用数量。
- 临时配件必须进入配件主数据。
- 临时配件必须进入库存体系。
- 临时入库必须生成库存流水。
- 工单结算后按正常配件规则扣减库存。

禁止：

```text
临时配件只存在工单备注里
临时配件不生成库存流水
临时配件不进入配件主数据
```

---

### 4.8 支付与结算

第一版必须支持：

- 多次付款
- 混合付款
- 微信支付记录
- 支付宝支付记录
- 银联支付记录
- 现金或其他支付方式可通过字典扩展
- 支付金额
- 支付时间
- 收款人
- 支付备注

支付必须是明细记录，不得只在工单表中放一个总支付字段。

结算规则：

```text
实收金额 = 支付总额 - 退款总额
应收金额 = 配件销售金额 + 人工费 + 其他费用
实收金额 >= 应收金额 才允许工单标记为已结算
```

说明：

- 第一版不对接真实支付网关。
- 第一版只记录线下/人工确认后的支付结果。
- 第一版不做自动收款或自动对账。

---

### 4.9 退款管理

第一版必须支持：

- 定金退款记录
- 其他退款记录
- 退款金额
- 退款方式
- 退款时间
- 操作人
- 退款原因
- 退款备注

规则：

- 退款必须生成退款记录。
- 退款不得直接删除原支付记录。
- 退款会影响工单实收金额。
- 已结算后退款第一版先只记录并影响财务，不自动回滚库存和工单状态；确需反结算时由后续专门流程处理。

---

### 4.10 官方售后订单

第一版必须支持：

- 官方售后订单号备注
- 手动录入官方结算金额
- 标记是否官方结算
- 官方结算时间
- 官方结算备注
- 官方结算与客户支付分开统计

规则：

```text
客户支付 ≠ 官方结算
```

禁止：

```text
把官方结算金额混入客户支付金额
把客户支付金额混入官方结算金额
```

说明：

- 第一版不关心官方系统内部结算细节。
- 第一版不自动同步官方系统。
- 第一版由管理端手动录入官方结算金额并标记官方结算。

---

### 4.11 报销台账

第一版必须支持员工报销台账。

员工可提交：

- 报销人
- 报销用途
- 报销金额
- 备注
- 提交时间

报销状态：

```text
待确认
已确认
已驳回/取消
```

规则：

- 老板/有权限人员确认后，报销才计入运营成本。
- 待确认报销不计入成本。
- 已驳回/取消报销不计入成本。

说明：

- 第一版只做报销台账。
- 不做完整审批流。
- 不做自动打款。
- 不做凭证上传。
- 不做报销类型管理。
- 后续可扩展审批流、凭证、自动支付等能力。

---

### 4.12 财务统计

第一版必须支持基础财务统计。

收入包括：

```text
配件收入
人工费
其他收入
官方结算收入
```

成本包括：

```text
配件成本
报销成本
```

利润计算：

```text
利润 = 收入 - 成本
```

必须支持：

- 日报
- 月报
- 时间范围查询
- 客户支付收入统计
- 官方结算收入统计
- 配件成本统计
- 报销成本统计
- 利润统计

规则：

- 客户支付和官方结算必须分开统计。
- 财务报表应从业务明细中汇总，不允许随意手改利润。
- 第一版暂不统计房租、水电、工资等其他运营成本。
- 当前运营成本入口以报销台账为主。

---

### 4.13 Excel 导出

第一版必须支持：

- 工单列表导出
- 财务报表导出
- 利润报表导出
- 库存报表导出
- 报销台账导出

规则：

- 导出结果应与当前查询条件一致。
- 导出内容以管理端为主。
- 第一版不做复杂自定义报表模板。

---

### 4.14 微信小程序员工端

第一版小程序面向员工/前台/维修员。

必须支持：

- 登录
- 工作台
- 创建工单
- 查询库存
- 扫码或手动入库
- 工单处理
- 客户结算记录
- 报销提交

说明：

- 第一版不做客户端小程序。
- 小程序不承担最终业务判断。
- 小程序只负责录入、查询、提交操作。
- 后端负责库存、结算、权限、财务等最终判断。

---

### 4.15 网页管理端

第一版管理端必须支持：

- 登录
- 权限管理
- 字典配置
- 配件管理
- 库存管理
- 工单管理
- 支付/退款查看
- 官方结算录入
- 报销确认
- 财务报表
- Excel 导出

说明：

- 管理端是老板/管理员/财务的主要操作入口。
- 复杂管理能力优先放在管理端，而不是小程序端。

## 8. 范围变更规则

任何新需求进入 MVP 前，必须先回答：

```text
1. 是否影响当前维修 + 库存 + 支付 + 财务主链路？
2. 是否当前门店真实高频使用？
3. 是否可以通过人工方式暂时解决？
4. 是否会改变数据库核心模型？
5. 是否会影响库存、支付、退款、结算或财务口径？
6. 是否会导致 Codex 修改核心模块？
7. 是否会延迟第一版真实试运行？
```

判断原则：

```text
高频、刚需、影响主链路 → 可以进入 MVP
低频、锦上添花、可人工处理 → 暂缓
需要复杂基础设施 → 暂缓
影响库存/支付/财务核心规则 → 必须重新评审
```

## 9. AI Agent 执行边界

### 9.1 ChatGPT

负责：

- 需求分析
- 架构方案
- 文档输出
- 任务拆解
- Codex / Claude 任务卡
- 风险审查
- Opus 反馈吸收与修订

不负责：

- 直接假设代码现状

Codex 可处理：

- 支付退款结算

Codex 不得擅自：

- 改变库存预占时机
- 改变结算条件

- 将报销提交直接计入成本

---

### 9.3 Claude

Claude 可处理：

- 简单页面

- 列表
- 字段展示
- 文档同步
- 单元测试
- 接口测试
- 简单低风险 bug

Claude 不得擅自修改：

- 库存预占/释放/扣减逻辑

- 支付退款结算逻辑

## 10. MVP 完成判断

第一版 MVP 完成，不以“页面全部漂亮”为标准，而以核心业务闭环跑通为标准。

必须跑通：

```text
配件入库
  ↓
库存增加
```
