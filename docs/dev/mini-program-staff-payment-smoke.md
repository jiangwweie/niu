# Staff 记录支付 (M7B) Smoke Test 报告

## 环境配置
- **API_MODE**: `real`
- **BASE_URL**: `http://localhost:8080` (后端 dev 模式)
- **请求头模拟**:
  - `X-User-Id`: 1
  - `X-Store-Id`: 1

## 测试目标
验证小程序端 Staff 在针对处于 `PENDING_ACCEPT` 或已受理状态的工单执行「记录支付」操作时，能够正确触发后端的支付登记接口，完成前端页面实收金额 (`receivedAmount`) 的刷新呈现，且严格保障不发生任何越界的结算及库存流转动作。

## 测试步骤与结果

### 1. 场景 A: 正常登记单笔支付
- **前置准备**:
  - 创建工单草稿并填充明细。
  - 提交工单使其流转到 `PENDING_ACCEPT` 状态。
  - 确认初始财务数据（例：`receivableAmount = 200`, `receivedAmount = 0`）。
- **执行记录支付**:
  - 页面可见“记录支付”按钮。点击按钮调出表单弹窗。
  - 录入测试数据：支付金额 `100`，支付方式选择 `WECHAT` (微信)，添加自定义备注。
  - 确认记录。
- **状态验证**:
  - [x] 后端返回 200 OK，成功记录了 `payment_record`。
  - [x] 刷新后 UI 数据更新，页面显示「已收金额：¥100」。
  - [x] `workOrder.status` 保持 `PENDING_ACCEPT` 不变。

### 2. 场景 B: 多次收款场景
- **操作**:
  - 在前一次支付的基础上，再次点击“记录支付”按钮。
  - 录入剩余金额 `100`，选择 `ALIPAY` (支付宝)。
- **状态验证**:
  - [x] 支付动作顺畅完成，工单总计实收金额更新为 `200` (`receivedAmount = 200`)。
  - [x] 即便全款已收清，前端**不自动越俎代庖判定工单已结算**，且工单仍处于开放的待处理状态。

### 3. 边界与异常情况验证
- **输入合法性拦截**:
  - 尝试输入金额 `0` 或负数，前端点击“确认”时直接被 Toast 驳回：“请输入大于0的支付金额”。
  - 未选择支付方式即点确认，被 Toast 拦截提示：“请选择支付方式”。
- **防抖保护机制**:
  - 前端依靠 `paymentLoading` 参数在弹窗发起异步请求期间将主控按钮置为 Disable 状态，成功避免了因网络延时可能带来的同笔资金两度登记风险。
- **状态显隐隔离**:
  - 针对处于 `DRAFT`、`CANCELLED` 及 `SETTLED` 等状态的工单，“记录支付”入口在 WXML 层面直接消失或不渲染。
- **资金/业务衍生越界拦截确认**:
  - [x] 确认本次提交中，**没有生成 `CONSUME` 或新的 `RELEASE` / `RESERVE` 库存流水**。实际库存数字无任何异动。
  - [x] 确认**未牵连退款记录模块** (`refund_record` 为空)。
  - [x] 确认界面上**绝对隔离成本字段** (`costPriceSnapshot` 等)。

## 结论
**PASS**. M7B “记录支付”阶段实现了完美的前后端衔接。满足业务设计中的人工核账场景需求，财务款项呈现及时清晰，并且严格坚守了不自动对账、不自动结算的 MVP 限定规则。
