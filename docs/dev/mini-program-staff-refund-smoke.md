# Staff 记录退款 (M8B) Smoke Test 报告

## 环境配置
- **API_MODE**: `real`
- **BASE_URL**: `http://localhost:8080` (后端 dev 模式)
- **请求头模拟**:
  - `X-User-Id`: 1
  - `X-Store-Id`: 1

## 测试目标
验证小程序端 Staff 在执行「记录退款」操作时，前端登记逻辑完备且符合预期限制，成功与后端的 `POST /api/staff/work-orders/{id}/refunds` 对接，能动态体现 `receivedAmount`（已收金额）的实时扣除减小情况，同时严防在端侧触碰复杂的库存回退或反结算账目边界。

## 测试步骤与结果

### 1. 场景 A: 记录正常退款
- **前置准备**: 
  - 存在一个已处于 `PENDING_ACCEPT` 或 `ACCEPTED`，且已有实收金额（例：`receivedAmount = 100`，`receivableAmount = 200`）的工单。
- **执行退款**:
  - 在页面操作区点击“记录退款”。
  - 输入退款金额 `50`。
  - 选择退款方式（例：`WECHAT`）。
  - 输入必填的退款原因：“客户要求部分退款”。
  - 点击“确认退款”。
- **状态验证**:
  - [x] 后端返回 200 OK，成功记录 `refund_record`。
  - [x] Toast 提示成功，前端通过 `refreshWorkOrder` 获取新数据，UI 面板上的“已收金额”实时降低至 `50`。
  - [x] `workOrder.status` 等关键生命周期节点均保持不受影响（未越俎代庖自动取消）。

### 2. 边界与异常情况拦截
- **基础规则拦截**:
  - 输入金额 `0` 或空值，拦截并提示：“请输入大于0的退款金额”。
  - 不选择退款方式，拦截并提示：“请选择退款方式”。
  - 未填写“退款原因”，拦截并提示：“请输入退款原因”。
- **过载金额（超退）**:
  - 试图向只支付了 `100` 的工单发起 `200` 的退款。前端将发往后端，通过统一 Request 拦截器抛出 `PAYMENT_REFUND_AMOUNT_EXCEEDS_RECEIVED`（由后端控制拦截），成功防御业务侵入。
- **状态栏展示拦截**:
  - `DRAFT` 和 `CANCELLED` 的工单直接屏蔽退款入口，阻绝无效行为。

### 3. 极速发包与资金/业务衍生越界防守
- **并发防御**: 依托 `refundLoading` 状态锁定提交按钮，确保异步执行期间无重放攻击（重复点击导致多重扣款记录生成）。
- [x] 确认本次提交中，**没有新增、取消或更改原本的库存预占（RESERVE）、消耗（CONSUME）以及释放（RELEASE）动作**。未出现任何 UI 表象的库存异动。
- [x] 确认**未牵连修改原有的 `payment_record`（资金单向流水记录保持独立与安全）**。
- [x] 确认**完全未做真实支付网关退款的 SDK 发起**。
- [x] **无自动反结算及强行 SETTLED/CANCELLED**: 退款只管资金记账反馈数字减持。

## 结论
**PASS**. M8B 退款功能顺利通过联调与测试，小程序端表现为纯粹轻量的请求抛送与最新数据回执渲染，做到了各边界要求的不碰库存、不触发回调且不侵入结算机动流程。
