# admin-web 三态工单与收银状态机适配 冒烟测试指南

本指南旨在指导开发与测试人员在 `admin-web` 适配 M24B 后端新状态机（三态机制：进度、收银、库存）后，如何进行全链路的冒烟测试与功能验证。

## 1. 测试前置准备

### 1.1 确认后端基线与分支
- **前端分支**：`feature/m18-delivery-readiness`
- **后端基线**：`536be41 feat(workorder): implement clean-start repair and cashier state machine`
- **运行环境**：启动本地 `admin-web` 研发服务器 (`npm run dev`) 并在浏览器中访问。

### 1.2 实验性数据初始化
1. 访问系统中的 **试运行数据清理** (`/trial-data` 页面)。
2. 执行清理以清除旧版试运行业务数据（需输入确认文本 `CONFIRM_CLEAR_TRIAL_DATA`），之后重新创建或导入测试工单。

## 2. 测试场景与步骤

### 2.1 工单列表多维度状态与筛选
**测试目的**：验证工单列表能够正确展示三态（进度、收银、库存），并且搜索条件运作正常。

**测试步骤**：
1. 进入“工单管理”主列表页。
2. 检查表格中的状态标签列，应包含：
   - **工单进度**：新建中 (DRAFT)、维修中 (REPAIRING)、维修完成 (REPAIR_DONE)、已交付 (DELIVERED)、已取消 (CANCELLED)。
   - **收银状态**：无需收款 (NO_CHARGE)、未收款 (UNPAID)、部分收款 (PARTIAL_PAID)、已收齐 (PAID)、待退款 (REFUND_PENDING)、部分退款 (PARTIAL_REFUNDED)、已退清 (REFUNDED)。
   - **库存状态**：未预占 (NOT_RESERVED)、已预占 (RESERVED)、已扣减 (CONSUMED)、已释放 (RELEASED)。
3. 检查金额相关列，页面应展示中文标签：
   - **应收金额**
   - **收款总额**
   - **退款总额**
   - **净实收**
   - **待收金额**
   - **可退金额**
4. 验证筛选器：
   - 选择“进度状态”（对应旧版的“工单状态”），筛选应正确向后端发送 `status` 参数。
   - 选择“收银状态”，应在前端支持多维度筛选。

---

### 2.2 工单详情与下一步操作提示 (`nextStepTip`)
**测试目的**：验证侧边抽屉能展示正确的收银汇总，并根据当前工单的“进度、收银、库存”组合状态动态提示店长“下一步该做什么”。

**测试步骤**：
1. 点击任意工单的“详情”按钮，展开侧边抽屉。
2. 查看“收银与售后摘要”区域，确认展示了：
   - 应收金额、收款总额、退款总额、实收净额、待收金额、可退金额。
3. 查看顶部或显著位置的“下一步操作指引”：
   - **场景 A**：进度显示“新建中”
     - *期望提示*：待员工小程序端提交并预占库存以推进工单
   - **场景 B**：进度显示“维修中”
     - *期望提示*：维修中：库存已预占，可继续维修、记录收款；维修完成后可标记维修完成。
   - **场景 C**：进度显示“维修完成”，收银显示“未收款”或“部分收款”
     - *期望提示*：工单维修已完成。客户尚未付款，请先催款/记录收款，结清后即可交付关闭。
   - **场景 D**：进度显示“维修完成”，收银显示“已收齐”或“无需收款”
     - *期望提示*：工单维修已完成且款项已结清，请执行“交付关闭工单”操作。库存已在标记维修完成时扣减，交付关闭不再改变库存。
   - **场景 E**：进度显示“已交付”，收银显示“待退款”
     - *期望提示*：工单已交付结清，目前存在待售后退款款项，请尽快处理退款。
   - **场景 F**：进度显示“已取消”
     - *期望提示*：工单已取消，库存已自动释放。

### 2.3 状态流转动作与权限按钮控制
**测试目的**：验证前端按钮的展示与启用状态严格受后端返回的权限布尔值控制，且不允许绕过收款硬性交付。

**测试步骤**：
1. 打开工单详情抽屉，对照接口返回的 `permission` 字段及状态：
   - `canMarkRepairDone` $\to$ “标记维修完成” 按钮
   - `canDeliver` 且状态为已结清 $\to$ 启用“交付关闭工单”按钮
   - `canRecordPayment` $\to$ “记录收款” 按钮
   - `canRecordRefund` $\to$ “记录退款” 按钮
   - `canCancel` $\to$ “取消工单” 按钮
2. **测试未收齐交付屏蔽**：
   - 当工单进度显示“维修完成”，但收银状态显示“未收款”或“部分收款”时，**交付关闭工单**按钮必须处于**置灰禁用**状态，并且悬浮其上时必须显示 Tooltip 提示：“**请先收齐尾款后再交付关闭**”。
   - 即使绕过界面，内部核心逻辑中也必须进行二次阻断拦截，不显示交付确认框。

### 2.4 六大核心动作对话框交互与校验

#### A. 标记维修完成 (`mark-repair-done`)
1. **测试用例 1（非零应收）**：应收金额 > 0 元，点击“标记维修完成”。
   - *期望行为*：直接弹出确认框，确认后成功流转。
2. **测试用例 2（零应收）**：应收金额 = 0 元，点击“标记维修完成”。
   - *期望行为*：弹出对话框，**必须**选择或填写“无需收款原因”（Dropdown 可选：“保修内免费”、“首保赠送”、“客户自备配件”、“无收费项目”、“其他”）。若未选择，提交按钮置灰或报错拦截。

#### B. 记录收款 (`record-payment`)
1. 打开“记录收款”对话框。
2. 输入的收款金额**不能超过**当前工单的“待收金额” (`outstandingAmount`)。
3. *期望行为*：前端应对输入金额进行上限校验（例如使用 `el-input-number` 限制 `max` 属性）。

#### C. 追加非库存费用 (`add-non-inventory-charge`)
1. 当工单进度显示“维修完成”时，点击“追加非库存费用”按钮。
2. 输入费用类型（只允许“工时费”或“其他费用”，不允许“配件费”），输入金额，并且必须填写追加原因。
3. *期望行为*：提交后，不触发库存动作；追加后系统重新计算应收金额、待收金额和收银状态，列表及详情中的应收金额、待收金额和收银状态应即时更新。

#### D. 交付关闭 (`deliver`)
1. **只有满足以下条件时按钮才可点击，允许弹出确认框**：
   - 后端允许交付，且收银状态显示“已收齐”或“无需收款”，工单进度显示“维修完成”。
2. **测试用例 1（常规已收齐场景）**：
   - *期望行为*：弹出确认框，展示应收金额与实收净额，并显示绿色成功 Alert：“工单已结清。确认交付关闭后，工单将进入已交付状态；库存已在标记维修完成时扣减，本操作不再改变库存。”。确认后调用交付关闭接口，工单进度显示“已交付”。
3. **测试用例 2（无需收款场景）**：
   - *期望行为*：确认框中**展示“无需收款原因”**；显示黄色警告 Alert：“无需收款工单（原因：保修内免费）。确认交付关闭后，工单将进入已交付状态；库存已在标记维修完成时扣减，本操作不再改变库存。”。**不显示**“已收齐”或“已结清”字样。确认后成功交付。

#### E. 交付后退款 (`record-refund`)
1. **测试用例 1（普通记录退款）**：工单未交付（如进度显示“维修完成”），发起退款。
   - *期望行为*：弹出普通退款确认框（标题为“记录退款”），输入退款金额（不可超过可退上限 `refundableAmount`），退款原因必填。
2. **测试用例 2（交付后退款）**：工单处于“已交付”状态，点击“交付后退款”（只有后端允许时才显示该按钮）。
   - *期望行为*：弹出确认框（标题变为**交付后退款**以示区别）；对话框顶部必须展示**强提示 Alert**：`“重要提示：交付后退款只影响资金流水，不回滚库存，不重开工单。”`；**退款原因必须填写**。

#### F. 取消工单 (`cancel`)
1. 点击“取消工单”按钮。
2. *期望行为*：弹出二次确认框，警示“取消工单将释放所有预占库存并关闭此工单，此操作不可逆。是否确认取消？”，确认后成功取消，库存状态显示“已释放”。

## 3. 回归与异常处理测试

- **BigDecimal 精度问题**：确保输入框的金额、展示金额均保留两位小数，不允许出现 `NaN` 或 JavaScript 浮点数多位小数（如 `1.0000000000000002`）。
- **操作人与时间**：每次状态变更后，列表及详情中的更新时间、操作人等基础审计字段应能正确渲染。
- **防止重复点击**：每个对话框的提交按钮，在网络请求处于 Pending 状态时必须置为 `loading` 或 `disabled`，严防重复点击导致的并发多次请求。
