# M22A 试运行 UI 文案与交互收口 - Smoke 测试与验收说明书

本说明书记录了针对 trial-v0.3.0 版本在试运行验收中发现的问题所做的 UI 文案抛光与交互收口成果，旨在为系统 Owner 及现场验收人员提供清晰的验证指引。

## 二、小程序工单详情收银操作区优化

### 1. 优化点与设计细节
* **收银操作卡片化**：将原来散落且偏长的底部悬浮操作区（`action-section`）移除，并在工单详情主页面内聚合成一个精简的 **“收银操作”卡片**。
* **收款术语中文化**：全面将原有的 “记录支付”、“线下支付”、“支付金额” 等偏向支付侧的词汇，修改为更符合店面实际收银口径的 **“记录收款”、“线下收款”、“收款金额”**。
* **财务四项核心指标网格**：在卡片顶部以紧凑的网格形式，清晰展示店员最关心的 4 项金额：
  * **应收金额**（保留两位小数展示，如：`¥150.00`）
  * **已收金额**（保留两位小数展示，如：`¥100.00`）
  * **待收金额**（若大于 0 则高亮红色，清晰提示欠款，如：`¥50.00`）
  * **可退金额**（自动绑定最大退款限额为当前的已收金额，如：`¥100.00`）
* **压缩说明文案**：废除大段的开发性解释（如“以后端校验为准”等冗长文字），精简为一条温馨而坚定的操作提示：
  > “操作结果以系统校验为准。”
* **结算按钮点击阻断**：
  * 当 **待收金额 > 0** 时，结算按钮展示为灰色次级状态，但不使用 native `disabled`（避免点击无响应）。
  * 店员点击该置灰结算按钮时，系统会弹出 Toast 明确阻断提示：“`请先完成收款，当前待收 ¥xx.xx`”，起到强有力的指引效果。
* **按钮精简与状态校验**：
  * 已结算（`SETTLED`）或已取消（`CANCELLED`）状态下，该收银操作区域的 “记录收款”、“记录退款”、“结算工单” 按钮将自动隐藏，避免冗余和误触。
* **危险操作隔离**：
  * 将 “取消工单” 按钮剥离出收银主操作区，移至最下方独立的 **“其他操作”** 卡片中。
  * 精简弹窗说明文字，只保留核心指引（“确认取消工单吗？取消后将释放预占库存，但不会自动退款。”），简单直接。

### 2. 草稿页同步优化 (举一反三)
* 在工单创建/草稿页面（`create-work-order-placeholder`）中，同步完成“记录支付” -> “记录收款”的文案替换与技术性弹窗文本精简，确保全小程序内交互、用词高度一致。

## 三、admin-web 财务报表页面文案中文化

### 1. 技术/DTO字段替换
对财务指标卡、拆分栏和表格中的英文 API/DTO 属性名进行了彻底的汉化替换：
* **净利润 (Profit)** → **净利润**
* **客户收入 (customerIncome)** → **客户实收收入**
* **官方结算收入 (officialIncome)** → **官方结算收入**
* **配件成本 (partsCost)** → **配件成本**
* **报销成本 (reimbursementCost)** → **已确认报销成本**
* **已结算工单数 (settledWorkOrderCount)** → **已结算工单数**
* **已确认报销数 (confirmedReimbursementCount)** → **已确认报销数**

### 2. 财务口径规范描述
大顶栏 Alert 及底部 **“口径说明”** 卡片中，公式描述全面重构为标准中文财务口径：
1. **总收入** = 客户实收收入 + 官方结算收入
2. **总成本** = 配件成本 + 已确认报销成本
3. **净利润** = 总收入 - 总成本
4. **客户实收收入** = 收款金额 - 退款金额
5. 所有金额均保留两位小数。空数据或无流水时，金额统一展示为 `¥0.00`。

## 四、admin-web 全局展示排查结果 (举一反三)

1. **英文字段名**：
   * `customerIncome`, `officialIncome` 等核心财务字段名仅作为 DTO 属性传递在 API 交互中，已在所有的财务报表和 Dashboard 界面中完成中文化，无任何英文遗漏。
   * `permissionCodes` 属于“系统管理 - 用户权限”模块中展示给高级管理员/店长做底层权限比对的原始代码标识，且在表格中配有对应的中文翻译，该设计符合管理端系统的常规标准。
2. **后端枚举值直接展示**：
   * 工单状态（如 `PENDING_ACCEPT`）和支付方式（如 `WECHAT`, `ALIPAY`）等在所有的 Vue 界面均有对应的 `Map`（例如 `DRAFT: '草稿', WECHAT: '微信'`) 进行转换，不存在直接将原始大写下划线字符串渲染给用户的情况。
3. **开发态词汇**：
   * 对项目进行了全局搜索，未发现任何在用户可见页面展示 `mock`、`placeholder`、`dev`、`Build`、`Phase` 等调试性词汇的问题。
4. **错误码展示**：
   * 接口报错（如 401/403/500 等）已被 axios 全局 `request` 拦截器接管，能够将错误信息解析为友好的中文 `ElMessage` 弹窗（如“权限不足”、“数据保存失败”等），不暴露底层的英文 Exception 编码。

## 五、金额与空状态统一排查

* **金额展示**：管理端所有的列表、卡片指标均内聚采用了全局 `<MoneyText>` 组件，自动实现 `¥` 符号前缀、千分符隔离以及强制保留 2 位小数，格式完美统一。
* **空状态**：对于暂无数据的列表，Element Plus 表格默认提供“暂无数据”空图，不需要额外处理。
* **操作确认**：结账、取消工单、分配配件等敏感操作均具有 `ElMessageBox.confirm` 二次确认弹窗保护，杜绝误触。

## 六、验收指引与测试路径

### 1. 小程序收款与结算验证
* **测试用例 1：待收工单结账阻断**
  1. 进入小程序工单详情，选取一个“待接单”或“已接单”且有费用明细的工单（假设应收 ¥100.00，已收 ¥0.00，待收 ¥100.00）。
  2. 观察收银操作区：“待收金额”为红色高亮 `¥100.00`，“结算工单”按钮处于灰色次级样式。
  3. 点击“结算工单”，验证系统弹出 Toast 阻断提示：“`请先完成收款，当前待收 ¥100.00`”，且不打开结算 Dialog。
* **测试用例 2：记录收款与结账流转**
  1. 点击“记录收款”按钮，选择收款方式（如“微信”），输入收款金额 `50.00`，点击确认收款。
  2. 验证收银卡片自动刷新，变为：已收 `¥50.00`，待收 `¥50.00`。
  3. 再次点击“记录收款”，输入收款金额 `50.00`，点击确认。
  4. 验证待收金额变为 `¥0.00`，“结算工单”按钮自动恢复为高亮 Primary 样式。
  5. 点击“结算工单”，弹出精简的结算确认框，输入备注并确认，工单流转为“已结算”，同时收银卡片操作按钮全部安全隐藏。
* **测试用例 3：危险操作取消验证**
  1. 进入草稿状态或未结算工单，滚动至底部“其他操作”卡片。
  2. 点击“取消工单”，验证弹窗提示内容精简为“`确认取消工单吗？取消后将释放预占库存，但不会自动退款。`”。

### 2. 财务报表中文化验证
1. 登录管理后台（admin-web），点击“财务管理” -> “财务报表”菜单。
2. 观察顶部 Alert：口径说明均采用全中文展现。
3. 观察财务指标卡：原英文 `Profit`、`customerIncome` 等已全部替换为“净利润”、“客户实收收入”、“官方结算收入”等标准财务汉字。
4. 观察右下方口径说明卡片：所有公示说明均采用全中文，布局紧凑美观。
