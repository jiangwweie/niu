# Admin Web 官方售后结算 (M11B) Smoke Test 报告

## 环境配置
- **端**: admin-web
- **API_MODE**: `real` (对接后端本地开发环境)
- **请求头模拟**: `Authorization` token 等由现有统一的 request wrapper 自动添加并承载

## 测试目标
确保 admin-web 的“官方售后结算”页面与后端的 `OfficialAfterSalesController` API 实现无缝对接。此模块属于完全隔离并平行于门店端客户收银逻辑的存在，前端必须能展示最新的汇总并安全地下发修改命令，一切深层业务逻辑交由后端管控。

## 测试步骤与验证结果

### 1. 列表与详情查询验证
- **场景**: 打开“官方售后结算”菜单。
- **操作**: 触发 `GET /api/admin/official-after-sales` 获得分页列表；点击某一行“查看”。
- **结果**: 
  - [x] 分页列表数据成功映射到 `tableData` 并渲染，字段包含：工单编号、客户信息、车型、官方订单号、客户实收金额、官方结算状态、官方结算金额与时间等。
  - [x] 点击“查看”成功触发 `GET /api/admin/work-orders/{workOrderId}/official-after-sales`，在右侧抽屉无损展示出该条工单具体的全量详情。

### 2. 状态扭转流与交互防御验证
- **前置**: 选取一条 `settlementStatus` 为 `PENDING` 的单据。
- **场景 A：录入官方订单号**
  - **操作**: 点击“录入订单号”，填入 `OS-10086`。
  - **结果**: 
    - [x] 成功请求 `POST .../order-info`。
    - [x] 若跨店或重复录入已被使用的官方单号（由 M11A 后端支持的同门店唯一性约束），拦截器能将服务端抛回的 Error Message 弹出，有效拦截提交。
- **场景 B：标记结算**
  - **操作**: 点击“标记已结算”，填入合法金额。
  - **结果**: 
    - [x] 成功请求 `POST .../settle`。
    - [x] 如果金额填 0 或负数，前端做轻量 `<el-input-number :min="0">` 拦截。
    - [x] 成功结算后，列表刷新，状态变更为 `SETTLED`。
- **场景 C：状态防卫验证**
  - **操作**: 观察 `SETTLED` 或 `NOT_REQUIRED` 单据的操作列。
  - **结果**: 
    - [x] “录入订单号”、“标记已结算”、“无需结算”等功能按钮均被隐匿，从端测阻断修改行为，以后端准则为核心。
- **场景 D：标记无需结算**
  - **操作**: 选取 `PENDING` 单据，点击“无需结算”，填写原因。
  - **结果**:
    - [x] 成功请求 `POST .../no-settlement-required`。
    - [x] 原因非空校验生效。
    - [x] 列表刷新，状态变更为 `NOT_REQUIRED`。

### 3. 极速发包与资金/业务衍生越界防守
- [x] 确认本次提交中，**前端从未伪造结算时间或操纵工单原有的客户实收额**。
- [x] 确认**未牵连任何 `payment_record` / `refund_record`**（两套资金账目彻底剥离）。
- [x] 确认**完全未做打款接口接驳**，此处仅供入账登记标记。
- [x] 确认**没有介入对账报表及跨店权限设计**，这些由后续迭代或在后端把控。

## 结论
**PASS**. M11B 接口对接圆满落地。Admin 前端忠实地承担了展示与指令抛送的角色，操作状态流转闭环完美适配 M11A 的后端核心策略，实现低侵入高可用。
