# Staff 结算工单 (M9B) Smoke Test 报告

## 环境配置
- **API_MODE**: `real`
- **BASE_URL**: `http://localhost:8080` (后端 dev 模式)
- **请求头模拟**:
  - `X-User-Id`: 1
  - `X-Store-Id`: 1

## 测试目标
验证小程序端 Staff 发起「结算工单」请求时，能否顺畅与后端的 `POST /api/staff/work-orders/{workOrderId}/settle` 交互，并安全遵循系统定义的只起“触发器”作用，将所有的扣减库存和状态流转交由后端接管。

## 测试步骤与结果

### 1. 场景 A: 满足前置条件顺利结算
- **前置准备**: 
  - 工单状态为 `PENDING_ACCEPT` 或 `ACCEPTED` 等。
  - 实收金额（`receivedAmount`）通过先前的支付动作达到了可结算阈值要求。
- **执行结算**:
  - 点击“结算工单”唤起 Dialog，确认无误点击。
- **状态验证**:
  - [x] Toast 提示“结算成功”。
  - [x] 前端调用 `refreshWorkOrder` 自动刷新工单详情，`workOrder.status` 更新为 `SETTLED`。
  - [x] UI 重新渲染后，“结算工单”以及其他如“记录支付/退款”的按钮全部屏蔽隐藏，成为真正的只读工单。
  - [x] 成功驱动后端的真实扣除并生成 CONSUME，**端上零处理**，一切遵从后端。

### 2. 边界与异常情况拦截
- **基础状态拦截**:
  - 在小程序界面上，`DRAFT`、`CANCELLED` 或原本已是 `SETTLED` 的工单被强行不渲染结算按钮。
- **实收金额不足拦截**:
  - 在工单欠款或后端策略判定不可结算时点击提交。
  - **拦截动作**: 前端不去解析或拆分原因，原样把由后端抛出的类似 `PAYMENT_WORK_ORDER_CANNOT_BE_SETTLED` Exception Msg，通过 Toast 展示给了端上用户，有效制止结算。
- **防抖锁定防重**:
  - 执行 `settleLoading = true` 避免了在网速慢时产生因多点击带来的并发请求。

### 3. 极速发包与资金/业务衍生越界防守
- [x] 确认本次提交中，**没有在前端模拟库存扣减。零 CONSUME 伪造流**。
- [x] 确认**未牵连任何 `payment_record` / `refund_record` 新增**。
- [x] 确认**未进行真实的资金收款/付款动作处理及跳转**。
- [x] 确认**没有介入官方结算与报销流程**。财务数据依旧纯净交由后端判定计算与下发。

## 结论
**PASS**. M9B 阶段实现了工单生命周期最后一个核心环节：结算的完美闭环。所有状态变化及库存收尾完全交由服务端主导，在兼顾防并发及提示交互的同时实现了极其克制的 MVP 要求！
