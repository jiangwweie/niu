## 1. 文档目的

本文档用于明确系统中**不能被随意改动、不能被前端绕过、不能被 AI 简化掉**的核心业务规则。

本文档不设计数据库表，不写接口实现，不写代码，而是先确定：

1. 工单状态怎么流转？
2. 库存什么时候预占、释放、扣减？
3. 配件和临时配件怎么管理？
4. 支付、退款、结算之间是什么关系？
5. 官方售后结算和客户支付怎么区分？
6. 报销什么时候计入成本？
7. 财务报表的收入、成本、利润口径是什么？
8. 哪些规则必须由后端控制？
9. 哪些行为必须留下流水或日志？
10. Codex 和 Claude 的实现边界是什么？

本文档确认后，后续所有设计和实现必须遵守。

## 2. 核心原则总览

本系统的核心原则是：

```text
工单驱动业务
库存用流水记账
支付用明细记账
退款不能删除原支付
官方结算和客户支付分开
报销确认后才入成本
财务从明细汇总
状态变化由后端控制
小程序和管理端不能绕过业务规则
```

实现层面必须坚持：

```text
1. 金额字段使用精确小数，Java 使用 BigDecimal。
2. 库存变化必须有库存流水。
3. 支付和退款必须有明细记录。
4. 工单结算必须校验实收金额。
5. 关键状态变化必须校验前置状态。
6. 关键动作必须防止重复执行。
7. 所有业务表预留 store_id。
8. 操作类数据必须记录操作人和操作时间。
9. 可配置项不得散落硬编码。
10. MVP 不引入复杂自动化流程。
```

## 8. 工单状态规则

### 8.1 MVP 工单状态

第一版工单状态：

```text
待接单
已接单
已定件
已到件
已结算
已取消
```

建议后端状态编码：

```text
PENDING_ACCEPT      待接单
ACCEPTED            已接单
PART_ORDERED        已定件
PART_ARRIVED        已到件
SETTLED             已结算
CANCELLED           已取消
```

### 8.2 状态流转规则

建议 MVP 状态流转：

```text
待接单 → 已接单
已接单 → 已定件
已定件 → 已到件
已到件 → 已结算

待接单 → 已取消
已接单 → 已取消
已定件 → 已取消
已到件 → 已取消
```

也允许根据门店实际简化为：

```text
创建工单
  ↓
提交工单
  ↓
处理中
  ↓
已结算 / 已取消
```

但数据库和代码中应保留扩展空间。

### 8.3 已结算状态规则

工单进入 `已结算` 必须满足：

```text
实收金额 >= 应收金额
```

并且：

```text
工单未取消
工单未重复结算
库存预占记录存在或可验证
```

### 8.4 已取消状态规则

工单进入 `已取消` 必须满足：

```text
工单未结算
工单未重复取消
```

取消时必须：

```text
释放预占库存
生成库存释放流水
记录取消原因
```

### 8.5 状态变更记录

工单状态变化必须记录：

```text
工单 ID
原状态
新状态
操作人
操作时间
变更原因或备注
```

### 8.6 禁止规则

禁止：

```text
前端直接传 status=SETTLED 绕过后端结算逻辑
前端直接传 status=CANCELLED 绕过库存释放逻辑
无状态校验直接修改工单状态
已结算工单重复结算
已取消工单重复取消
```

## 9. 工单编辑规则

### 9.1 未提交 / 未结算工单

DRAFT 阶段工单可以编辑部分信息，例如：

```text
客户信息
车辆信息
费用项目明细（charge items）
备注
```

DRAFT 阶段可对费用项目明细进行：

```text
新增费用项目
修改费用项目
删除费用项目
```

支持三类费用项目：

```text
charge_type = PART     配件费（关联 part_id，影响库存）
charge_type = LABOR    工时费（不影响库存）
charge_type = OTHER    其他费用（不影响库存）
```

DRAFT 阶段所有费用项目操作均不影响库存，不生成库存流水。

### 9.2 已提交但未结算工单

如果工单已经提交并产生库存预占，需要调整费用项目时，必须区分类型：

```text
PART 类型费用项目：
  减少或删除 → 释放预占，写 RELEASE 流水
  增加或新增 → 校验可用库存，预占差量，写 RESERVE 流水
  库存不足时整体回滚

LABOR / OTHER 类型费用项目：
  仅调整费用项目金额和明细
  不影响库存，不生成库存流水
```

MVP 建议：

```text
已提交工单原则上不随意修改费用项目明细。
如需修改，必须走 adjust-charge-items 动作。
该动作必须按 charge_type 分别处理，确保 PART 类型库存同步。
```

### 9.3 已结算工单

已结算工单不允许普通调整费用项目明细：

```text
费用项目明细
配件销售价
工时费
其他费用
库存消耗
应收金额
```

如需处理错误，后续应设计专门的售后、退款、反结算或调整流程。

MVP 不实现复杂反结算。

### 10.3 第三方配件

第三方配件由系统自动生成内部编码。

要求：

```text

可打印条形码

```

### 10.4 配件销售价规则

配件销售价在工单中手动填写。

第一版不要求：

```text
默认价格表
自动带出销售价
复杂价格策略
会员价
折扣价
```

work_order_charge_item 上下文规则：

```text
1. PART 类型费用项目明细的 unit_price 表示本次配件销售单价。
2. PART 类型 line_amount = quantity × unit_price。
3. PART 类型 cost_price_snapshot 保存本次成本价快照。
4. PART 类型 line_cost_amount = quantity × cost_price_snapshot。
5. 配件销售价不从默认价格表强制带出，仍由工单费用项目明细中手动填写。
6. LABOR / OTHER 类型也通过 unit_price / line_amount 表达收费金额，但不关联 part_id，不影响库存。
7. 不再使用 work_order.labor_fee / work_order.other_fee 作为主要金额来源。
```

### 10.5 配件停用规则

配件停用后：

```text
不应再被新工单选择
历史工单和库存流水仍然保留
```

禁止直接删除已有业务引用的配件。

## 13. 库存模型规则

### 13.1 库存三数量

库存必须区分：

```text
actual_qty      实际库存
available_qty   可用库存
reserved_qty    预占库存
```

### 13.2 三者含义

#### actual_qty

实际库存，表示门店账面实际持有数量。

#### available_qty

可用库存，表示还能被新工单预占的数量。

#### reserved_qty

预占库存，表示已经被提交工单占用，但尚未结算正式消耗的数量。

### 13.3 数量关系

通常情况下：

```text
actual_qty = available_qty + reserved_qty
```

在发生调整、异常处理、历史数据迁移等情况时，可以通过库存流水追溯原因。

### 13.4 禁止规则

禁止：

```text
只维护一个 stock 数量
直接 update 库存数量而不生成流水
让库存变成负数
前端直接修改库存数量
无权限人员调整库存
```

## 14. 库存预占规则

### 14.1 预占时机

只有在：

```text
提交工单
```

时预占库存。

明确禁止：

```text
添加配件到工单草稿时立即预占库存
```

### 14.2 预占库存影响

提交工单时，只对 charge_type = PART 且 inventory_affecting = 1 的费用项目明细预占库存：

```text
available_qty -= 使用数量
reserved_qty += 使用数量
actual_qty 不变
```

charge_type = LABOR 和 OTHER 的明细不参与库存预占。

### 14.3 预占条件

预占前必须校验：

```text
工单状态允许提交
费用项目明细 charge_type = PART
inventory_affecting = 1
part_id IS NOT NULL
配件存在
配件未停用
available_qty >= 使用数量
使用数量 > 0
```

### 14.4 预占流水

提交工单产生预占时，必须生成库存流水。

流水类型：

```text
RESERVE
```

### 14.5 防重复预占

同一工单不能重复提交导致重复预占。

必须通过：

```text
工单状态校验
提交标识
事务控制
```

防止重复操作。

## 15. 库存释放规则

### 15.1 释放时机

当未结算工单取消时，释放预占库存。

### 15.2 释放库存影响

取消工单时，只对 charge_type = PART 且 inventory_affecting = 1 的费用项目明细释放预占库存：

```text
reserved_qty -= 使用数量
available_qty += 使用数量
actual_qty 不变
```

charge_type = LABOR 和 OTHER 的明细不参与库存释放。

### 15.3 释放条件

释放前必须校验：

```text
工单未结算
工单未取消
存在预占记录
```

### 15.4 释放流水

释放库存必须生成库存流水。

流水类型：

```text
RELEASE
```

### 15.5 防重复释放

已取消工单不能再次取消。

禁止重复释放库存。

## 16. 库存扣减规则

### 16.1 扣减时机

只有工单结算时，才正式扣减库存。

### 16.2 扣减库存影响

结算工单时，只对 charge_type = PART 且 inventory_affecting = 1 的费用项目明细扣减库存：

```text
reserved_qty -= 使用数量
actual_qty -= 使用数量
available_qty 不变
```

charge_type = LABOR 和 OTHER 的明细不参与库存扣减。

### 16.3 扣减条件

扣减前必须校验：

```text
工单未取消
工单未结算
实收金额 >= 应收金额
费用项目明细 charge_type = PART
inventory_affecting = 1
存在预占库存
reserved_qty >= 使用数量
```

### 16.4 扣减流水

正式扣减库存必须生成库存流水。

流水类型：

```text
CONSUME
```

### 16.5 防重复扣减

已结算工单不能再次结算。

必须防止重复扣减实际库存。

## 18. 工单费用项目明细规则

### 18.1 统一费用项目明细模型

工单使用统一的费用项目明细表 work_order_charge_item。

work_order_charge_item 是工单收费/维修项目的唯一明细来源，替代原有的配件明细 + labor_fee + other_fee 分散模式。

### 18.2 charge_type 分类

每个费用项目明细有一个 charge_type：

```text
PART     配件费      关联 part_id，影响库存，参与配件收入和配件成本统计
LABOR    工时费      不关联 part_id，不影响库存，参与人工费收入统计
OTHER    其他费用    不关联 part_id，不影响库存，参与其他收入统计
```

### 18.3 inventory_affecting 规则

```text
charge_type = PART      → inventory_affecting = 1
charge_type = LABOR     → inventory_affecting = 0
charge_type = OTHER     → inventory_affecting = 0
```

只有 inventory_affecting = 1 的明细才参与库存预占、释放和扣减。

### 18.4 应收金额汇总

工单应收金额 receivable_amount 由所有费用项目明细汇总：

```text
receivable_amount = Σ work_order_charge_item.line_amount
```

### 18.5 收入按 charge_type 分类

```text
配件收入 = Σ charge_type = PART 的 line_amount
人工费收入 = Σ charge_type = LABOR 的 line_amount
其他收入 = Σ charge_type = OTHER 的 line_amount
```

### 18.6 成本按 charge_type 分类

```text
配件成本 = Σ charge_type = PART 的 line_cost_amount
```

### 18.7 DRAFT 阶段规则

DRAFT 阶段可对费用项目明细进行新增、修改、删除，均不影响库存，不生成库存流水。

### 18.8 已提交未结算阶段规则

已提交未结算工单如需调整费用项目，必须走 adjust-charge-items 动作：

```text
PART 类型：同步库存预占差异，生成 RESERVE / RELEASE 流水
LABOR / OTHER 类型：仅调整金额，不影响库存
```

### 18.9 已结算阶段规则

已结算工单不允许普通调整费用项目明细。

### 18.10 labor_fee / other_fee 字段说明

work_order 表中的 labor_fee 和 other_fee 字段已废弃，不再作为工单费用的主要来源。

应收金额和收入分类均由 work_order_charge_item 按 charge_type 汇总。

### 18.11 与工单动作的关系

```text
提交工单（submit）：遍历 charge_type = PART 且 inventory_affecting = 1 的明细预占库存
取消工单（cancel）：遍历 charge_type = PART 且 inventory_affecting = 1 的明细释放预占
结算工单（settle）：遍历 charge_type = PART 且 inventory_affecting = 1 的明细扣减库存
调整明细（adjust-charge-items）：PART 类型同步库存差异，LABOR/OTHER 类型只改金额
```

## 19. 临时配件规则

### 19.1 临时配件定义

临时配件是指在工单处理过程中发现系统中不存在，需要现场新增并立即用于当前工单的配件。

### 19.2 临时配件必须进入主数据

临时配件必须：

```text
创建配件主数据
进入库存体系
生成库存流水
关联当前工单
```

### 19.3 临时入库数量

MVP 规则：

```text
临时入库数量默认等于本次工单使用数量
```

### 19.4 临时配件库存流程

临时配件属于 charge_type = PART 的费用项目明细。

流程：

```text
创建临时配件
  ↓
临时入库
  ↓
生成 INBOUND 流水
  ↓
加入工单费用项目明细（charge_type = PART，inventory_affecting = 1）
  ↓
提交工单时 PART 类型明细 RESERVE
  ↓
结算工单时 PART 类型明细 CONSUME
```

### 19.5 禁止规则

禁止：

```text
临时配件只写在备注里
临时配件不入库
临时配件不生成流水
临时配件绕过正常库存扣减
```

## 20. 支付规则

### 20.1 支付必须是明细

支付不得只记录在工单单字段中。

必须支持：

```text
一个工单多笔付款
一笔付款一种支付方式
多种支付方式混合付款
```

### 20.2 支付记录字段

支付记录至少包含：

```text
工单 ID
支付金额
支付方式
支付时间
收款人
操作人
备注
```

### 20.3 支付方式

支付方式来自字典。

默认包括：

```text
微信
支付宝
银联
现金
其他
```

### 20.4 支付金额规则

支付金额必须：

```text
大于 0
使用 BigDecimal
保留合理小数位
```

### 20.5 支付不等于结算

有支付记录不代表工单已结算。

工单是否可结算必须由：

```text
实收金额 >= 应收金额
```

判断。

## 21. 退款规则

### 21.1 退款必须是明细

退款必须生成退款记录。

不得通过删除或修改原支付记录来表达退款。

### 21.2 退款记录字段

退款记录至少包含：

```text
工单 ID
退款金额
退款方式
退款时间
操作人
退款原因
备注
```

### 21.3 退款金额规则

退款金额必须：

```text
大于 0
不能超过当前可退金额
```

当前可退金额建议为：

```text
支付总额 - 已退款总额
```

### 21.4 退款对实收影响

实收金额计算：

```text
实收金额 = 支付总额 - 退款总额
```

### 21.5 已结算后退款规则

MVP 规则：

```text
已结算后可以记录退款
退款影响财务实收
不自动回滚库存
不自动改变工单状态
不自动反结算
```

复杂反结算、退货、库存退回流程后续单独设计。

## 22. 应收、实收与结算规则

### 22.1 应收金额

应收金额计算：

```text
应收金额 = Σ work_order_charge_item.line_amount
```

即所有费用项目明细的 line_amount 汇总，包括：

```text
配件费明细（charge_type = PART）的 line_amount
工时费明细（charge_type = LABOR）的 line_amount
其他费用明细（charge_type = OTHER）的 line_amount
```

### 22.2 实收金额

实收金额计算：

```text
实收金额 = 支付总额 - 退款总额
```

### 22.3 结算条件

工单允许结算的必要条件：

```text
实收金额 >= 应收金额
工单未取消
工单未结算
库存已预占
```

### 22.4 结算动作影响

结算动作必须同时完成：

```text
校验结算条件
扣减库存
生成库存消耗流水
更新工单状态为已结算
记录结算人和结算时间
```

### 22.5 多收款处理

若：

```text
实收金额 > 应收金额
```

MVP 允许结算。

多收部分是否退款，由人工处理并生成退款记录。

## 23. 官方售后规则

### 23.1 官方售后字段

官方售后工单必须支持：

```text
官方售后订单号
官方结算金额
官方结算状态
官方结算时间
官方结算备注
```

### 23.2 官方结算录入

官方结算金额由管理端手动录入。

第一版不自动同步官方系统。

### 23.3 官方结算与客户支付分离

必须明确：

```text
客户支付收入 ≠ 官方结算收入
```

二者都可以进入收入统计，但必须分开列示。

### 23.4 官方结算不影响工单客户结算

官方结算金额不应直接作为客户已支付金额。

客户支付是否结清，仍然按支付记录和退款记录计算。

### 23.5 官方结算状态

建议状态：

```text
未结算
已结算
无需结算
```

具体状态可在数据库设计阶段确认。

## 25. 财务统计规则

### 25.1 财务统计来源

财务统计必须来自业务明细：

```text
工单明细
支付记录
退款记录
官方结算记录
库存成本记录
报销记录
```

不允许手动直接修改利润。

### 25.2 收入口径

收入包括：

```text
配件收入 = Σ charge_type = PART 的 line_amount
人工费收入 = Σ charge_type = LABOR 的 line_amount
其他收入 = Σ charge_type = OTHER 的 line_amount
官方结算收入 = official_after_sales 中已结算官方金额
```

### 25.3 成本口径

成本包括：

```text
配件成本 = Σ charge_type = PART 的 line_cost_amount
报销成本 = 已确认报销金额
```

### 25.4 利润口径

利润：

```text
利润 = 配件收入 + 人工费收入 + 其他收入 + 官方结算收入 - 配件成本 - 报销成本
```

### 25.5 客户支付收入

客户支付收入建议计算：

```text
客户支付净收入 = 支付总额 - 退款总额
```

### 25.6 官方结算收入

官方结算收入来自：

```text
已标记官方结算的官方结算金额
```

### 25.7 配件成本

配件成本来自工单消耗配件的成本记录。

MVP 阶段可采用：

```text
工单使用配件时记录当时成本价
```

防止后续成本价变化影响历史利润。

### 25.8 报销成本

报销成本来自：

```text
已确认报销金额
```

### 25.9 当前不统计

MVP 暂不统计：

```text
房租
水电
工资
社保
折旧
其他固定运营成本
```

当前运营成本入口以报销台账为主。

## 27. 小程序端业务规则

### 27.1 小程序定位

小程序是员工高频操作入口。

小程序负责：

```text

查询
扫码
提交
查看状态
```

### 27.2 小程序不能做最终判断

小程序不得作为以下规则的最终判断来源：


这些必须由后端判断。

例如禁止：

```text

body: { status: "SETTLED" }
```

必须走后端命令动作：

```text
提交工单
取消工单
结算工单
记录支付
记录退款
提交报销
```

## 31. 事务规则

### 31.1 必须使用事务的场景

以下场景必须使用数据库事务：

```text

提交工单 + 库存预占 + 库存流水 + 工单状态更新
取消工单 + 库存释放 + 库存流水 + 工单状态更新
结算工单 + 结算校验 + 库存扣减 + 库存流水 + 工单状态更新
退款记录 + 实收金额相关校验
报销确认 + 报销状态更新
官方结算录入 + 官方结算状态更新
```

### 31.2 事务失败处理

如果事务中任一步失败，整体应回滚。

禁止出现：

```text
工单已结算但库存未扣
库存已扣但工单未结算
入库数量已加但没有流水
退款已记录但金额校验失败
```

