# admin-web 三态工单与收银状态机适配 冒烟测试指南

本指南旨在指导开发与测试人员在 `admin-web` 适配 M24B 后端新状态机（三态机制：进度、收银、库存）后，如何进行全链路的冒烟测试与功能验证。

## 1. 测试前置准备

### 1.1 确认后端基线与分支
- **前端分支**：`feature/m18-delivery-readiness`
- **后端基线**：`536be41 feat(workorder): implement clean-start repair and cashier state machine`
- **运行环境**：启动本地 `admin-web` 研发服务器 (`npm run dev`) 并在浏览器中访问。

### 1.2 实验性数据初始化
1. 访问系统中的 **实验数据初始化** (`/trial-data` 或相应配置页面)。
2. 确保完成了 M24B 新状态机专用测试数据的一键重置与预加载。

---

## 2. 测试场景与步骤

### 2.1 工单列表多维度状态与筛选
**测试目的**：验证工单列表能够正确展示三态（进度、收银、库存），并且搜索条件运作正常。

**测试步骤**：
1. 进入“工单管理”主列表页。
2. 检查表格中的状态标签列，应包含：
   - **工单进度**：新建中 (DRAFT)、维修中 (REPAIRING)、维修完成 (REPAIR_DONE)、已交付 (DELIVERED)、已取消 (CANCELLED) 等。
   - **收银状态**：无需收款 (NO_CHARGE)、未收款 (UNPAID)、部分收款 (PARTIAL_PAID)、已收齐 (PAID)、待退款 (REFUND_PENDING)、部分退款 (PARTIAL_REFUNDED)、已退清 (REFUNDED) 等。
   - **库存状态**：未预占 (NOT_RESERVED)、已预占 (RESERVED)、已扣减 (CONSUMED)、已释放 (RELEASED)。
3. 检查金额相关列：
   - **应收金额** (`paymentTotal`)
   - **净实收** (`actualReceivedTotal` = 支付总额 - 退款总额)
   - **待收金额** (`outstandingAmount`)
4. 验证筛选器：
   - 选择“进度状态”（对应旧版的“工单状态”），筛选应正确向后端发送 `status` 参数。
   - 选择“收银状态”，应在前端支持多维度筛选（或适配最新本地状态视图）。

---

### 2.2 工单详情与下一步操作提示 (`nextStepTip`)
**测试目的**：验证侧边抽屉能展示正确的支付汇总，并根据当前工单的“进度、收银、库存”组合状态动态提示店长“下一步该做什么”。

**测试步骤**：
1. 点击任意工单的“详情”按钮，展开侧边抽屉。
2. 查看“支付汇总”区域，确认展示了：
   - 应收总额、已付总额、退款总额、净实收、待收/待退额。
3. 查看顶部或显著位置的“下一步操作指引”：
   - **场景 A**：进度为 `DRAFT` (新建中) 
     - *期望提示*：工单处于新建中，请先“标记开始维修”以预占库存。
   - **场景 B**：进度为 `REPAIRING` (维修中)，库存为 `RESERVED` 
     - *期望提示*：维修中，若维修完毕且费用确认，请点击“标记维修完成”；如有需要，可先追加非库存费用。
   - **场景 C**：进度为 `REPAIR_DONE` (维修完成)，收银为 `UNPAID`/`PARTIAL_PAID` (未结清)
     - *期望提示*：维修已完成，客户尚未结清费用。请先点击“记录收款”，结清后再进行“交付”；或可直接“交付关闭”（系统将予以未结清警告）。
   - **场景 D**：进度为 `REPAIR_DONE` (维修完成)，收银为 `PAID`/`NO_CHARGE` (已结清)
     - *期望提示*：维修已完成且费用已结清，请点击“交付关闭”将车辆交付客户，并正式扣减库存。
   - **场景 E**：进度为 `DELIVERED` (已交付)，收银为 `REFUND_PENDING` (待退款)
     - *期望提示*：工单已交付，但存在多收或退单，需进行“记录退款”处理。
   - **场景 F**：进度为 `CANCELLED` (已取消)
     - *期望提示*：工单已取消，关联预占库存已释放。

---

### 2.3 状态流转动作与权限按钮控制
**测试目的**：验证前端按钮的“显示/隐藏/置灰”状态严格受后端返回的权限布尔值控制，而非前端硬编码。

**测试步骤**：
1. 打开工单详情抽屉，对照接口返回的 `permission` 字段：
   - `canMarkRepairDone` $\to$ “标记维修完成” 按钮
   - `canDeliver` $\to$ “交付关闭” 按钮
   - `canRecordPayment` $\to$ “记录收款” 按钮
   - `canRecordRefund` $\to$ “记录退款” 按钮
   - `canCancel` $\to$ “取消工单” 按钮
2. 验证各个生命周期下，不满足权限的按钮是否已经安全隐藏或禁用，防止非正常状态下非法越权请求。

---

### 2.4 六大核心动作对话框交互与校验

#### A. 标记维修完成 (`mark-repair-done`)
1. **测试用例 1（非零应收）**：应收金额 > 0 元，点击“标记维修完成”。
   - *期望行为*：直接弹出确认框，确认后成功流转。
2. **测试用例 2（零应收）**：应收金额 = 0 元，点击“标记维修完成”。
   - *期望行为*：弹出对话框，**必须**选择或填写“无需收款原因”（Dropdown 可选：“保修内免费”、“首保赠送”、“客户自备配件”、“无收费项目”、“其他”）。若未选择，提交按钮置灰或报错拦截。

#### B. 记录收款 (`record-payment`)
1. 打开“记录收款”对话框。
2. 输入的收款金额**不能超过**当前工单的“待收金额” (`outstandingAmount`)。
3. *期望行为*：前端应对输入金额进行上限校验（例如使用 `el-input-number` 限制 `max` 属性）。

#### C. 追加非库存费用 (`add-non-inventory-charge`)
1. 点击“追加非库存费用”按钮（如在维修中阶段）。
2. 输入费用类型（工时费、其他费用），输入金额，并输入追加原因。
3. *期望行为*：提交后，列表及详情中的应收金额、待收金额应即时更新。

#### D. 交付关闭 (`deliver`)
1. **测试用例 1（已结清）**：收银状态为 `PAID`/`NO_CHARGE`。
   - *期望行为*：直接弹出标准交付确认框，确认后工单进度流转为 `DELIVERED`，库存状态流转为 `CONSUMED` (已扣减)。
2. **测试用例 2（未结清）**：收银状态为 `UNPAID`/`PARTIAL_PAID`。
   - *期望行为*：弹出**带警告样式**的交付确认框，明示“当前工单尚未结清，仍有 X 元待收。是否确认直接交付关闭？”，并强调交付后无法在此界面继续发起收款。确认后允许正常交付。

#### E. 交付后退款 (`record-refund`)
1. **测试用例 1（未交付退款）**：工单未交付（如 `REPAIR_DONE`），发起退款。
   - *期望行为*：弹出普通退款确认框，输入退款金额（不可超过可退上限 `refundableAmount`）。
2. **测试用例 2（已交付退款）**：工单处于已交付 `DELIVERED` 状态，点击“记录退款”。
   - *期望行为*：由于已交付，对话框顶部展示**黄色警告 Banner**：“当前工单已交付结案，退款可能会改变财务入账与统计结果，请谨慎操作！”。且退款金额同样不得超过 `refundableAmount`。

#### F. 取消工单 (`cancel`)
1. 点击“取消工单”按钮。
2. *期望行为*：弹出二次确认框，警示“取消工单将释放所有预占库存并关闭此工单，此操作不可逆。是否确认取消？”，确认后成功取消，库存状态流转为 `RELEASED` (已释放)。

## 3. 回归与异常处理测试

- **BigDecimal 精度问题**：确保输入框的金额、展示金额均保留两位小数，不允许出现 `NaN` 或 JavaScript 浮点数多位小数（如 `1.0000000000000002`）。
- **操作人与时间**：每次状态变更后，列表及详情中的更新时间、操作人等基础审计字段应能正确渲染。
- **防止重复点击**：每个对话框的提交按钮，在网络请求处于 Pending 状态时必须置为 `loading` 或 `disabled`，严防重复点击导致的并发多次请求。
